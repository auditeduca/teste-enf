5. STARTUP OBRIGATÓRIO

Execute exatamente nesta ordem:

1) Ler este START HERE.

2) Ler no Supabase o control_ref do work item em cko_governance.object_versions. Identificar tanto a versão cronologicamente mais recente quanto a versão efetiva. Uma versão com state=PLANNED_NOT_ACTIVATED, DRAFT ou equivalente NÃO substitui a última versão ACTIVE_CONTROL/efetiva. No piloto de Design System, o objeto é CKO-PMO-DS-PARALLEL-CONTROL-001.

3) Ler cko_governance.agent_work_items e localizar apenas os itens atribuídos ao seu agent_id/provider/papel.

4) Ler checkpoints, evidence bundles, artifact execution contexts e eventos relacionados ao seu work item quando aplicável.

5) Confirmar baseline_version, input_hash, evidence_refs e último checkpoint.

6) Se existir versão mais nova do baseline ou conflito de hash, NÃO executar: registrar STALE_BASELINE.

7) Executar somente a microtarefa atribuída.

8) Salvar resultado/checkpoint versionado no Supabase.

9) Espelhar documentação legível no Drive sem sobrescrever histórico.

10) Fazer readback dos dois lados.

11) Só então buscar a próxima microtarefa governada.

Sua primeira ação deve ser somente:

READ → RECONCILE → IDENTIFY ASSIGNED MICROTASK → REPORT STARTING STATE.

10. INTERRUPÇÃO / TOKENS / CONTEXTO

Antes de uma interrupção previsível, grave checkpoint com progresso, último item concluído, próximo item, evidências e hashes. Se a sessão terminar, a nova sessão deve reconstruir o estado pelo último checkpoint, não pelo histórico de chat.

Rate limit temporário = THROTTLED.

Quota/crédito esgotado = QUOTA_EXHAUSTED.

Credencial ausente/expirada = AUTH_REQUIRED.

Fim de janela de contexto = CONTEXT_EXHAUSTED; salvar checkpoint e continuar em nova microtarefa/sessão.

Silêncio não é PASS. Na reconciliação seguinte, ausência de checkpoint pode ser classificada pelo orquestrador como SUSPECT/DORMANT conforme política vigente.

11. EVIDÊNCIA E ANTIALUCINAÇÃO

14. FINALIZAÇÃO DA FRENTE

Quando o escopo técnico executável estiver concluído:

1) Não iniciar nova wave automaticamente.

2) Emitir READY_FOR_BACKUP para o orquestrador responsável.

3) Pausar mutações.

4) Preservar todos os HOLDs válidos.

5) Após ACK do orquestrador: executar backup Supabase + Drive + readback.

6) Emitir FRONT_COMPLETE e FRONT_STOPPED, ou equivalente específico da camada.

7) Registrar a conclusão também no próprio chat/log da frente quando a conversa for retomada, incluindo: estado final, denominadores, PASS/HOLD/FAIL, findings, learning, hashes, backup/readback e motivo de qualquer HOLD remanescente.

8) O chat/log da frente não é fonte canônica; ele é espelho humano da conclusão registrada no control plane.

15. REGRA PARA CONVERSAS PARALELAS

Uma conversa paralela não deve assumir que está ativa apenas porque foi criada. Ao ser retomada, deve:

READ current state → compare last known checkpoint → reconcile → execute only next governed microtask.

Se o trabalho já tiver sido concluído por outra frente ou pelo orquestrador, documentar no próprio chat: TASK ALREADY COMPLETED / NO FURTHER MUTATION AUTHORIZED e encerrar.

16. PRIMEIRA RESPOSTA ESPERADA DO WORKER

Antes de executar, reporte somente:

- agent/provider identificado;

- control version mais recente + control version efetiva;

- work_item/microtask atribuída;

- baseline/hash confirmados ou STALE;

- dependências/HOLDs relevantes;

- estado inicial: READY | HOLD | STALE | UNAVAILABLE.

Somente depois prossiga para a execução governada.
